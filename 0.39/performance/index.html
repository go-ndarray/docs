Performance — go-ndarray vs NumPy

go-ndarray against the pinned NumPy on one core, both sides: the method, one row per public function, and what is still unmeasured.

You are reading the documentation of an outdated version, whose text may no longer be accurate. Go to the latest version.

Mirrored from docs/perf.md at v0.39.0.

The table is perf-table.md, generated by refbench (go-scikit/refbench v0.1.2) from perf.json; nothing in it is edited by hand. The rules are those of the go-scikit performance campaign (go-scikit/roadmap#27):

  • One core on both sides. GOMAXPROCS=1 for Go, and the reference worker runs with OMP_NUM_THREADS, OPENBLAS_NUM_THREADS, MKL_NUM_THREADS, VECLIB_MAXIMUM_THREADS at 1. GOMAXPROCS=1 must also be in the environment of the test binary: ndarray/fft rests on go-fft/fft, which reads it once at init (go-fft/fft#107).
  • The pinned reference: NumPy 2.5.4 (bench/refs.txt, hashes included), Python 3.12.12 through uv. The earlier page of this repository compared multicore Go with single-threaded NumPy 2.2.4 and is kept as perf-history.md for its kernel-level analysis only.
  • Interleaved rounds, one statistic: a round is one sample per side, alternating which runs first; the verdict is on the median with quartiles.
  • Load gate: no timing verdict at a 1-minute load of 8 or more (-perf.run refuses and writes nothing).
  • Same data: every array argument is lo + (hi-lo) * frac(i * 0.618...), built in Go and in NumPy; TestDataParity compares the SHA-256 of both sides' bytes (24 distinct argument sets, complex ones included, all equal), and TestRefSmoke runs every NumPy call once.
  • One case per public function (a function with several shapes of use has several rows, Array.SumAxis/axis0 and /axis1), or a named exemption with its reason in perf-exempt.md. CI fails on a public function with neither.

float32 Max and Min (v0.39.0)

Array.Max and Array.Min on float32 call go-simd/floats Float32Max and Float32Min; ndarray’s own extrema32 kernels were removed (#110). go-simd/floats v0.15.0 adds an AVX2 path on amd64 (#111). On one Zen 3 core, 16 384 elements take 0.77 µs (Max) and 0.74 µs (Min), against 1.40 and 1.32 µs with SSE2 and 2.61 to 3.32 µs with NumPy 2.5.4. At 1 M elements the timing is memory-bound and NumPy varied from 64 to 113 µs across runs, so no ranking is claimed at that size (go-simd/floats#46).

What a row times

Each row calls the Go function once on a vector of 100 000 elements (a 1000 x 100 matrix for the axis reductions, 128 x 128 for the matrix products, 64 x 64 for linalg, 65 536 points or 256 x 256 or 32 x 32 x 32 for fft), and the NumPy call on the same data. The result is allocated by the call on both sides; the *Into rows write into a preallocated array on both sides (out=). The random rows draw 100 000 values from a generator built once outside the timed loop (default_rng(1) / DefaultRNG(1), RandomState(1), np.random.seed(1)), so the constructor is not in the interval. Views (Reshape, Slice, Transpose, Ravel) are views in NumPy; where Go copies, the row says so.

fft rows include the plan on both sides: ndarray/fft builds or fetches a plan per call, numpy.fft keeps its own plan cache warm after calibration. The scipy.fft comparison of the transforms themselves is go-fft/fft’s.

Value parity is not checked here: each package’s own tests compare its results with NumPy’s fixtures (random/numpy_test.go, linalg/testdata, fft/testdata).

Running it

cd bench
GOMAXPROCS=1 go test -run TestPerf -cpu 1 .               # CI mode: allocations, table, public-function inventory
GOMAXPROCS=1 go test -run TestPerf -cpu 1 -perf.run .     # measure; writes docs/perf.json and docs/perf-table.md
GOMAXPROCS=1 go test -run TestPerf -perf.record .         # allocation counts only (status: deferred)
go test -run 'TestDataParity|TestRefSmoke' -perf.parity . # needs uv

Status

The table at this commit is deferred: the host was at a 1-minute load of 8 to 80 all day, so only the allocation counts are recorded (exact under any load). There is no timing verdict, and no row is claimed faster or slower. The first -perf.run at a load below 8 replaces it, and refbench issues drafts one issue per slower row.

Defects visible from the allocation counts alone are filed: #103 (Choice: 200 013 allocations for 100 000 draws) and #104 (linalg decompositions: 90 to 276 allocations per 64 x 64 call).
